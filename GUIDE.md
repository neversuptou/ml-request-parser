## 1. Задача

Из поста с IT-вакансией (Telegram-каналы аутстафф-компаний) получить текст по шаблону:

```
Найден запрос

Номер заявки: 30597
Наименование проекта: —
Позиция: Разработчик 1С
Уровень: Senior
Опыт работы: —
Длительность проекта: —
Рейт: —
Требования: ...
Будет преимуществом:            (только если есть)
...
Выполняемы задачи на проекте: ...
Локация проживания: Россия; Удаленно; (MSK) Москва
Контакты: —
Дополнительная информация:      (строки, не попавшие в поля, кроме мусора)
Количество специалистов: 2
⚠️ Проверить вручную: ...       (только если разбор ненадёжный)
```

Раньше разбирал прод (`tg_application`): DeepSeek по API, а при его недоступности — regex-шаблоны
по каналам. Цель — бесплатно и локально, и не хуже DeepSeek.

## 2. Как устроено сейчас

**Подход: построчная классификация.** Каждая строка поста -> одно из полей, `header` (заголовок
секции) или `other`. Затем значения полей собираются из строк.

```
текст поста
  │
  ├─ parser/regex_rules.py   подписанные поля ("Ставка: 2200", "Грейд: Senior") + секции
  │
  ├─ parser/line_model.py    модель ставит метку каждой строке (+ уверенность 0..1)
  │     └─ parser/line_post.py  поправки структуры поста (см. ниже)
  │
  ├─ parser/regex_rules.extract_embedded
  │                          поля ВНУТРИ чужих строк: номер заявки, грейд, срок
  │                          ("ID:14918_Аналитик 1С Senior в телеком")
  │
  └─ parser/extractor.py     слияние + рендер шаблона
```

Правила слияния (`extractor.py`):
- одиночные поля — regex приоритетнее (подпись надёжнее), КРОМЕ позиции, контактов и локации
  (`MODEL_FIRST`): там regex угадывает эвристикой и ошибается, модель надёжнее;
- списки (требования, задачи, преимущества) — модель;
- пустые поля добираются `extract_embedded`;
- строки `other` без мусора (хэштеги, ссылки, инструкции к резюме) -> «Дополнительная информация»;
- «⚠️ Проверить вручную»: нет позиции / нет ни требований, ни задач / модель не уверена (< 0.6)
  в 3+ строках.

Поправки структуры (`line_post.py`) — то, что модель по одной строке не видит:
- подзаголовок внутри списка («Диагностика и устранение ошибок:» под «Задачи:») — продолжение списка;
- заголовки других полей («О проекте:», «Контакты:», «Location:») — список закончился;
- секция-инструкция («В резюме должны быть:», «При подаче укажите:») — не требования (метка `junk`);
- подписанное поле («Роль специалиста: X», «Часовой пояс: MSK») важнее догадки модели;
- строка из одних хэштегов — не позиция.

Модели (выбирается автоматически, `load_line_model`):
- `model/lines-rubert/` — rubert-tiny2 (нейросеть, дообучена), если есть;
- `model/lines-baseline.joblib` — TF-IDF + логистическая регрессия (быстрая), запасной вариант.
На качество по полям они почти равны (см. раздел 6).

## 4. Как пользоваться и как проверять

```bash
python cli.py post.txt                      # разобрать пост
uvicorn api.main:app --port 8000            # сервис

# после изменений правил/модели:
python scripts/prepare_lines.py && python scripts/check_rules.py
python scripts/train_lines_baseline.py
python scripts/field_gold.py score          # главная цифра: прод vs наша по значениям полей
python scripts/field_score.py --from 34     # честная выборка (посты, на которых правила не подстраивались)
```

Переобучить нейросеть (~1 ч на CPU; не уходит в сон, чекпоинты каждые 800 шагов):

```bash
python scripts/train_lines_bert.py --base cointegrated/rubert-tiny2 --out model/lines-rubert --epochs 2 --lr 1e-4
# если оборвалось — то же самое + --resume
```

## 5. Хронология: что пробовали, что получилось, что нет

### 5.1. Делегирование в OpenCode — не сработало
`opencode-delegate.ps1` передаёт флаг `--auto`, которого нет в установленной версии `opencode run`
(выходит за 1.6 с). Запуск с `--dangerously-skip-permissions` заблокирован. Код писался напрямую.

### 5.2. NER по разметке DeepSeek — не сработал (F1 0.14 → 0.36)
Идея как в `ml-hr-rec-service`: DeepSeek — учитель, DistilBERT — ученик, разметка кусков текста (BIO).
- 1-й запуск: F1 0.14 → 0.21 за 2 эпохи. Причина: NER учится только на значениях, которые есть в тексте
  дословно, а DeepSeek пересказывал, склеивал пункты через «;», дописывал своё.
- Чистка разметки (разбивка склеенного, нечёткое сравнение, отброс постов < 60% покрытия,
  стаж убран из NER): F1 0.33 → 0.43 → итог **0.36** на тесте.
- Вывод: строгие границы кусков + шумная разметка учителя — тупик. Отказались.

### 5.3. Построчная классификация — сработала
Посты построены строками (каждая строка — требование, задача, локация…). Модель решает «к какому
полю строка», границы всегда точные. Быстрая модель (TF-IDF + логрег) сразу дала F1 0.79 против 0.36 у NER.

### 5.4. Данные из БД прода вместо выгрузки админки
- CSV админки (59 тыс. заявок) — без исходных текстов, только поля. Бесполезен для обучения.
- В таблице `template_application` есть колонка `source_text` (добавлена миграцией 0034).
  Тексты есть у 3736 заявок: 2071 разобраны шаблоном (поля — дословные куски текста),
  1665 — DeepSeek. Выгрузка SQL — см. `DATA_TODO.md`.
- 53 тыс. старых шаблонных заявок без текста можно докачать из Telegram (`scripts/fetch_tg_texts.py`),
  пока не понадобилось.

### 5.5. Разметка — главный рычаг качества
Шаблонные поля тоже «грязные»: шаблон захватывает текст до следующего маркера и настроен не на все поля.
Правила `regex_fill` (`scripts/prepare_lines.py`), каждое — из найденной ошибки:
- одиночное поле размечается одной строкой (шаблон «съедал» хвост);
- строка под заголовком секции получает поле секции (SkillStaff не вытаскивал списки → 13 тыс. строк были «не поле»);
- заголовок секции важнее «жадного» шаблона («Задачи:» → tasks);
- нумерованные подписи «9. Локация спеца:», номер заявки в первой строке («ВЗ-0234», «ID 175», «#1103/2»);
- «Плюсом:», «Дополнительные требования:», «Приветствуется:» → преимущества;
- «Заработная плата по договоренности», «Формат оплаты:» → рейт; «Удалёнка», «разница во времени к МСК» → локация;
- «Заполнить гугл форму», «Резюме направляйте @x» → контакты; «Дополнительные требования: Нет» → не поле.

Эффект: авто-разметка совпадает с ручным эталоном 83% → **95%**; быстрая модель 77% → 86% строк верно.

Грабли:
- «1С:Предприятие» принималось за подпись «Опыт:» и обрывало список требований → разделитель подписи
  только `:` перед пробелом;
- «Проектирование БД:» совпадало с «проект» → граница слова `\b` после ключевого слова;
- правка одного правила регрессировала другое — после каждой правки `check_rules.py`.

### 5.6. Сборка полей — баги, которые съедали качество
- позицию regex брал из первой строки («#аутстаф»), контакты — первую строку с «@» → для позиции,
  контактов, локации модель приоритетнее (`MODEL_FIRST`): поля 9.0 → **9.9 из 11**;
- regex обрезал «+» («Middle+» → «Middle»);
- в позиции оставался номер («14918_Аналитик») → отрезается.

### 5.7. Нейросеть: DistilBERT — не дождались, rubert-tiny2 — ок, но выигрыша почти нет
- `distilbert-base-multilingual-cased` на CPU: ~19 с/шаг, 4838 шагов ≈ 25 ч. Ночью ПК ушёл в сон
  на 26%, чекпоинтов не было — всё потеряно. Отсюда: запрет сна в скрипте + чекпоинты каждые 800 шагов.
- `cointegrated/rubert-tiny2` (29 млн параметров, RU+EN): ~1 с/шаг, **~1 ч**. Тест: 92.0% строк, F1 0.914.
- По полям — почти как быстрая модель (90.7% vs 90.2%). Потолок не в модели, а в подходе и данных.

### 5.8. Сравнение с продом (DeepSeek/шаблоны)
- Первая попытка (по построчному эталону) дала «прод 56–75%, наша 90%» — **нечестно**: построчный
  эталон не видит полей внутри строк («ID:14918_... Senior в телеком» — номер, грейд, проект),
  DeepSeek их правильно достаёт и за это штрафовался.
- Вывод из этого: у нас реальный недостаток — одна строка = одно поле. Закрыт `extract_embedded`
  (номер, грейд, срок из любого места): +6 п.п.
- Честная линейка: `data/field_gold.json` — вручную значения полей, как заполнил бы менеджер (24 поста).
  Сравнение мягкое: краткий верный ответ не штрафуется, основы слов (падеж не ошибка).

Замеченные ошибки DeepSeek на этих постах: выдумал срок «длительный», прочитал «оплата в течение
1-1,5 мес.» как рейт «1500», подставил контакт из чужой заявки (разбор из кэша).

### 5.9. Разбор реального поста 30597 (1С, ESB Datareon)
Ошибки: позиция = хэштеги; задачи обрезаны на подзаголовках; инструкция к резюме ушла в требования;
часовой пояс не в локации. Все исправлены поправками структуры (`line_post.py`).
Попутная регрессия: «О проекте:» считался подзаголовком списка → проект уходил в задачи
(88.3% вместо 89.6%) → известные заголовки других полей закрывают список → **90.4%**.

## 6. Результаты (на 25.09.2026)

**Главная цифра — эталон значений полей, 24 поста** (`scripts/field_gold.py score`):

| | Прод (DeepSeek + шаблоны) | Наша |
|---|---|---|
| Полей верно | 78.8% | **90.4%** |
| Заявок без единой ошибки | 7 / 24 | 9 / 24 |

Оговорки: эти 24 поста входят в те, на которых подстраивались правила (результат наш слегка завышен);
«прод» — смесь DeepSeek и шаблонов, сам DeepSeek, по оценке, ~85%; эталон писался с видом на оба ответа.

По полям (наша): номер 96%, позиция 100%, грейд 100%, срок 96%, рейт 92%, задачи 96%, проект 88%,
требования 83%, локация 79%, контакты 67%. Слабые места — **контакты и локация**.

Цели (договорились): 95% полей, 60–70% заявок без ошибок, ключевые поля (позиция, рейт, локация,
контакты, номер) — 95%+.

## 7. Метрики — как читать

- **Строки верно** — доля строк с правильной меткой. Не равна качеству полей.
- **Поля верно** — сколько из 11 полей заявки заполнено правильно (одиночное — совпадение по смыслу,
  список — найдено ≥ 80% пунктов и лишних ≤ 20%). Это главная метрика.
- **Честная выборка** — посты 34+, на них правила не подстраивались. Посты 0–33 использовались
  для поиска ошибок разметки, на них цифры завышены.
- F1 — среднее точности и полноты; для NER считался строго по границам кусков (поэтому был таким низким).
